Four surfaces, one runtime

Not four apps. Four sets of
tool definitions.

Every feature is a tool plus a prompt spec, never a new subsystem. That is the only reason a full education system is credible in thirty hours — and it is the argument that turns ambition from a red flag into a design claim.

01

ClassDrop

The teacher's phone raises an access point with no uplink behind it and serves a web client. Students scan a QR and land in the class in their browser. Notes, PDFs, worksheets, quizzes and audio push in real time, with delivery receipts.

AirDrop for a room where nobody has AirDrop
02

StudyDesk

Import a chapter and it becomes a queryable study companion whose answers are grounded strictly in that source, with the line cited. Ask something outside it and the answer is "that isn't in your material."

NotebookLM, minus the notebook leaving the phone
03

ClassTest

Questions auto-generate from any indexed source under a hard schema, get verified — grounding first, then Symja for anything numeric — and land on every joined browser at once. Grading is local, so the heatmap builds instantly at T0.

A wrong answer key is worse than no quiz
04

StepTutor

It checks whether each line of your working is equivalent to the one above it and flags the first line where that stops being true. Then it plays an animated walkthrough, narrated in Tamil or Hindi, rendered frame-by-frame from the CAS trace.

The premise

Bad internet is the country.
Not no internet.

One bar, 2G fallback, packet loss, a data pack that ran out on the 20th, a hostel basement, a village at six in the evening. Apps do not fail cleanly there — they hang, retry and spin, and the student watches a loader. So connectivity is treated as a dial, not a switch, and the app is built to be best at the bottom of it.

T0 — Dark no network at all

Every feature completes, fully. Nothing degrades, nothing queues, nothing spins. This is the design target, not the fallback — and it is what the demo opens on, with airplane mode visibly switched on.

the design target

T1 — Weak 2G · one bar

Text and deltas sync opportunistically; media queues. Everything is compressed and resumable, and the UI never blocks on any of it. The student never learns that the network is bad.

faster, not possible

T2 — Good real bandwidth, briefly

Burst sync. Genuinely hard questions may escalate to cloud — but only when the local verifier reports low confidence and the network is actually good. Local-first, cloud-optional, which is also how the sponsor's AI credits get used honestly.

richer, still optional

The design rule: every feature must complete at T0. T1 and T2 make it faster or richer — never possible. Flip the strip on the phone above and check that claim yourself.

The technical heart

EduQoo Core — a local agent runtime.

Everyone at a hackathon can call a local model. Almost nobody builds the harness that makes a 2B model reliable enough to be trusted with a child's homework. That harness is the project; the education system is what it is pointed at.

EduQoo Core local agent runtime · one process, on the phone
  1. Router

    Local-first. Escalates to cloud only when the verifier reports low confidence and the network is genuinely good.

  2. Context budgeter

    Token accounting against a finite attention budget, with remaining capacity fed back after every tool call.

  3. Assembler

    system │ core memory │ retrieved chunks │ scratchpad

  4. Planner loop

    Step limit, timeout, cancel. It is allowed to give up.

  5. Tool registry

    Typed Kotlin schema compiled to JSON Schema. Seven tools, deliberately non-overlapping — near-duplicates make a small model burn turns choosing.

    • cas.check()Symja — is line N+1 equivalent to line N?
    • retrieve()SQLite vector store, 768-dim, plus an FTS table
    • ocr()ML Kit — Latin and Devanagari only
    • speak()Android TTS, regional language, offline voice pack
    • quiz.generate()schema-constrained at the decoder
    • class.broadcast()push to every joined device over SSE
    • progress.write()per-student long-term memory
  6. Two-pass executor

    Pass 1 unconstrained — the model decides which tools to call, and they run. Pass 2 fully schema-constrained — the results are in context and the model only formats the answer.

  7. Verifier

    CAS ground truth for anything mathematical, a grounding check against the retrieved chunk for anything factual, schema validation for structure. Nothing reaches a student unchecked.

  8. Memory

    core (pinned, ~120 tokens) │ working (compacted on fill) │ archival

Gemma 4 E2B via LiteRT-LM  ·  Symja CAS  ·  SQLite  ·  Ktor CIO in a foreground service
Hard part 01

Constrained decoding is the foundation

LiteRT-LM enforces the JSON schema at the decoding level — the engine guarantees compliance instead of you parsing free text and hoping. On Gemma 4 edge builds that lifted a 24-way classification task by +0.35 and JSON generation by +0.90, for roughly 0.06s of latency. It buys about a model generation of reliability for free, which is why 2B is enough here.

Hard part 02

Tool Suppression, and the fix

Enable schema constraints and tool calling in the same pass and open-weight models quietly stop invoking tools — the grammar mask makes tool-call tokens unreachable while the output stays schema-valid. EduQoo Core uses transparent two-pass execution: pass 1 decides and runs tools, pass 2 formats under the schema. Open the runtime chip on the phone and you can watch both passes.

Hard part 03

A finite attention budget

Context length degrades quality through lost-in-the-middle effects long before the hard token limit. So: ~120 tokens of pinned core memory, working memory compacted on fill, raw tool results cleared once consumed, a scratchpad written to disk outside the window, top-k retrieval from today's chapter only, and seven deliberately non-overlapping tools.

The language model never decides whether the maths is right. A computer algebra system does.

The model only phrases the explanation. We will not hallucinate at a child learning calculus — and that is a property of the architecture, not a promise about the prompt.

Why this has to be the phone

The architecture requires the device.

A quarter of the hackathon score is device telemetry, and it is the quarter you cannot fake. Native Kotlin and Jetpack Compose — not Flutter, not a web wrapper — because everything load-bearing here lives at the native layer.

Accelerator access

LiteRT / QNN delegates, NNAPI and constrained decoding are native-layer concerns. A cross-platform wrapper hands them to you at arm's length or not at all — and constrained decoding is load-bearing for the whole verifier story, so arm's length is not an option.

Radios and services

The embedded Ktor server, the local-only hotspot and a sustained inference loop all need real foreground-service lifecycle and real permission handling. The phone is not running the app — the phone is the server the whole room is talking to.

Camera, mic and TTS with no bridge tax

CameraX and Android TextToSpeech called directly, with no serialisation hop per frame. The regional-language voice packs are downloaded once and then work with the radios off — which is the only reason the Tamil audio survives airplane mode.

Real utilisation, not simulated

Camera, mic, TTS, an on-device model, the hotspot radio and a foreground service, all doing genuine sustained work. The telemetry is real because the design needs it to be — not because the metric was gamed.

The honest part

What we deliberately do not build.

A clean "no, and here's why" beats a broken yes. These are roadmap, and saying so out loud is how you show you know where the edge is.

Generative video
Not feasible on-device, and it would hallucinate maths. The walkthrough is rendered from the CAS trace instead, which is why it cannot show a wrong step.
Tamil handwriting OCR
ML Kit Text Recognition v2 has no Tamil script model. Tamil is spoken output only, and we say so rather than promising it.
Live continuous camera explanation
Thermal throttling on a phone that has been building for twenty-eight hours. Single-shot inference only.
Auto-grading handwritten long-form answers
Unreliable, and a wrong grade on a child's work is a real harm — not a rounding error.
Cloud accounts, login, multi-school sync
Contradicts the entire premise. There is no account because there is no server that outlives the class.
Two minutes thirty

The demo, beat by beat.

Rehearsed aloud, timed, four times. It opens by killing the network and closes on the line that is the whole thesis.

0:00 Kill the network
Airplane mode on, visibly. Hotspot back on. "That is a local network with nothing behind it."
0:15 Recruit the jury
QR on screen. "Please take out your own phones and scan this." They land in the classroom in a browser, no install. This is the moment they remember.
0:45 Distribute
Photograph a board. Clean notes appear. Tap Push — every device in the room, including the judges', refreshes.
1:15 Tutor, at real difficulty
A worked integral with a planted error on line 3. It flags line 3 and explains in Tamil. "The model did not decide that. A computer algebra system did."
1:45 Show the runtime
One tap reveals the trace: tools called, tokens spent, verifier verdict, confidence. "Two-pass execution, because schema constraints suppress tool calls if you don't separate them."
2:10 Office Kit
Pull the analytics CSV to the laptop while the phone stays on the hotspot.
2:25 Close
"One phone. Thirty students. No installs, no data, no internet — and when the network comes back, it only gets better. It was never required."
